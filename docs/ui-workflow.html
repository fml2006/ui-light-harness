El target guía el resultado.

Layout y jerarquía esperados, conservando la marca del sitio actual. Una referencia externa no reemplaza logos, tipografías ni paleta.

El código guía la implementación.

Reutilizar componentes, tokens y estilos antes de extender. No reconstruir para imitar una captura.

El recorrido de una tarea

  1. Target + estado actual

    Abrir la ruta y capturar BEFORE. Fijar viewport, tema y datos. Si no se puede renderizar, detenerse.

  2. Auditoría agrupada

    Comparar toda la pantalla y localizar su componente/CSS. Registrar hasta ocho grupos de diferencias.

  3. Primer patch

    Modificar lo necesario, reutilizando lo existente. Registrar la primera pasada antes de editar.

  4. Render + comprobación

    Inspeccionar AFTER, comprobar interacciones y responsive. Comparar todos los targets del lote.

  5. Una corrección residual

    Solo si falta algo: agrupar residuos, corregir y validar otra vez. No iniciar una nueva exploración general.

  6. Cerrar o devolver

    Entregar estado, diff, capturas y checks. Si no alcanza, explicar el bloqueo sin tercera pasada.

DONE

Referencia cumplida y comprobaciones pertinentes realizadas. Si ocurre en la primera pasada, se termina ahí.

NEEDS_REVIEW / BLOCKED / ESCALATE

Diferencias pendientes, entorno incompleto o tarea fuera de alcance. Conservar evidencia y explicar la decisión necesaria.

Una pasada es un lote de edición y su validación. Desktop y mobile del mismo lote no cuentan como dos pasadas. La V1 registra este límite mediante instrucciones; no tiene un contador impuesto por software ni un tope duro de créditos.

Dónde conviene

  • Ajustar cards, formularios, spacing y tipografía.
  • Igualar una pantalla a una referencia concreta.
  • Corregir layout y responsive con componentes conocidos.
  • Pequeños cambios de markup sin alterar comportamiento.

Dónde cambia el modo

  • Autenticación, APIs, datos o reglas de negocio.
  • Estado complejo, arquitectura o refactor amplio.
  • Cambios compartidos cuyo impacto no se puede acotar.
  • Problema visual que supera las dos pasadas o la capacidad del modelo.

Cómo pedirlo

Instalá las reglas en tu app existente y abrí esa app en Codex. La guía USO.md explica la preparación y los pedidos cotidianos.

Usá UI Light. Actualizá /dashboard para que coincida con:

El proyecto necesita su mapa de arranque/capturas y autorización de consumo previamente establecidos. Este pedido no autoriza compras ni reemplaza el presupuesto.

Relación con el kit principal

Independiente: dev → Luna → autoverificación → entrega al dev. No necesita otro orquestador ni hace push.

Integración futura: orquestador → worker UI → evidencia → QA cruzado → aprobación del dev. Requiere adaptar el runner y transportar capturas; todavía no está conectado.

DONE visual no equivale al PASS del kit robusto. Una tarea gobernada por ese kit conserva sus controles.

Lo que ya está y lo que falta comprobar

Está definido el contrato, la configuración de proyecto y la memoria mínima. Falta comprobar con una app real si Luna entrega cambios aceptables en dos pasadas con menor costo total.
